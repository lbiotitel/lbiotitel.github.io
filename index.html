팀원이 코드 수정 없이 데이터만 추가해도 기능이 늘어나는 구조, 매니저 초기화 순서와 리소스 해제처럼 눈에 잘 띄지 않지만 프로젝트를 지탱하는 부분을 중요하게 생각합니다. 전체 코드는 GitHub에서 확인하실 수 있습니다.

😃

꾸준함과 끈기로 끝까지 완성합니다.

처음부터 기능을 많이 넣으려다 완성하지 못한 경험이 있어, 작은 프로젝트라도 짧게 끝까지 만드는 습관을 들였습니다. 60시간 목표의 강아지 자동 배급기에서 시작해 3주짜리 졸업 작품, 그리고 출시까지 점점 긴 프로젝트에 도전했습니다.

유닛을 모아 배치하고 6대6 자동전투로 35라운드를 진행하는 모바일 오토배틀러입니다. 팀장을 맡아 로비와 메타 시스템, 서버 연동, 데이터 저장 구조를 설계하고 구글 플레이 출시까지 진행했습니다. 화면 전환 시 리소스 로드와 해제, 서버 데이터의 비동기 처리, 팝업과 시트 UI를 나눠 관리하는 구조를 중점적으로 작업했습니다.

핵심 개발

1. 전역 매니저 구조와 재시작 처리

모든 매니저를 먼저 생성한 뒤 Initialize / Release로 순서대로 초기화와 해제를 해서 매니저끼리 서로 참조해도 null이 나지 않게 했습니다. 재시작 시에는 빈 씬을 거쳐 씬·리소스 해제 → 매니저 재초기화 → 타이틀 순서를 보장했고, 씬 전환은 빌더 패턴으로 묶어 호출하는 쪽에서 필요한 기능을 골라 쓸 수 있게 했습니다.

2. 시트, 팝업 UI 프레임워크

팝업은 기존 화면 위에 쌓이고 시트는 기존 화면을 교체하기 때문에 각각 별도의 컨테이너로 관리해, 화면마다 팝업과 시트 동작을 따로 구현하지 않아도 되게 했습니다. 모든 UI는 BaseUI를 상속하고 OpenUI<T>()로 열며, 닫힌 UI는 파괴하지 않고 풀링해서 재사용합니다.

3. 뒤끝 서버 연동 래퍼

콜백 기반 뒤끝 SDK를 UniTask async/await로 감싸 순차적인 코드로 쓸 수 있게 해 가독성 문제를 해결했고, 점검·요청 과다 같은 서버 에러를 이벤트 하나로 모아 에러 팝업을 한 곳에서 처리했습니다.

문제 해결

🔥 변경 없는 저장에도 반복되던 서버 호출과 저장 누락
상황

프로필, 재화, 에너지, 출석, 유닛, 아티팩트, 퀘스트 등 저장할 유저 데이터가 많아, 주기 저장 때마다 바뀌지 않은 데이터까지 서버에 보내고 있었습니다. 2인 개발이라 제 파트의 저장 코드를 검토해 줄 사람도 없었습니다.

원인

어떤 데이터가 바뀌었는지 추적하지 않았고, 데이터 종류마다 로드·저장 코드가 따로 흩어져 있었습니다.

해결
  • UserServerDataBase 추상 클래스로 저장 데이터를 묶고, 타입을 키로 하는 매니저에서 관리
  • IsDirty 플래그로 바뀐 데이터만 전송하고, 저장에 성공했을 때만 플래그 해제 (실패 시 다음 주기에 재시도)
  • 백그라운드 진입·종료 시 동기 저장, 오래 비운 뒤 복귀하면 이전 상태로 덮어쓰지 않도록 차단
  • 설계는 직접 하고, AI에게 놓쳤을 만한 부분을 후보로 받아 코드와 하나씩 대조하며 dirty 누락 필드를 수정
결과

저장 데이터를 8개 테이블로 나누고 바뀐 테이블만 보내도록 바꿔, 저장할 때마다 8번이던 호출이 1번으로 줄었습니다. 저장 대상에서 빠져 있던 필드 3개도 찾아 고쳤습니다.

알게 된 점

검토해 줄 사람이 없을 때는 바뀐 데이터를 사람이 신경 쓰기보다 코드가 추적하게 하는 게 안전하다는 걸 배웠습니다.

🔥 가챠 저장 실패 시 재화와 결과가 어긋나는 문제
상황

가챠는 재화 차감, 결과 반영, 서버 저장이 한 번에 일어나서, 중간에 하나라도 실패하면 재화만 사라지거나 결과만 지급되는 경우가 있었습니다.

원인

세 단계가 하나로 묶이지 않고 따로 처리돼, 중간에 실패하면 앞 단계를 되돌릴 방법이 없었습니다.

해결
  • 확률은 뒤끝 서버 확률표에서 받아와 클라이언트 조작을 막고, 앱 업데이트 없이 확률 변경
  • 로컬 반영 전에 재화와 유닛·아티팩트 데이터의 스냅샷을 만들고, 두 테이블을 하나의 트랜잭션으로 저장
  • 저장 실패나 예외가 나면 스냅샷으로 롤백하고 에러 이벤트 알림, 결과 UI는 저장 성공 후에만 표시
  • 뒤끝 SDK 호출(GachaBackEnd)과 게임 규칙(GachaService)을 분리
결과

저장이 실패해도 재화와 결과가 어긋나지 않고, 유저는 실패한 가챠 결과를 보지 않게 되었습니다. 네트워크가 불안정해도 성공과 실패 처리가 명확해졌습니다.

한계와 개선

재화 차감 값은 클라이언트가 계산해 저장하므로 메모리 변조까지는 막지 못합니다. 이후에는 서버 코드(뒤끝 펑션)에서 추첨, 차감, 지급을 한 번에 처리하도록 바꾸는 것이 목표입니다.

심연을 탐험하며 몬스터와 싸우고 보물을 얻어 영지를 발전시키는 액션 게임입니다. 언리얼 GAS의 데이터 구조를 참고해 스킬과 아이템 효과를 코드 수정 없이 데이터만으로 조합할 수 있게 만들었고, 장비를 바꿀 때마다 달라지는 스탯이 어긋나지 않도록 계산 구조도 따로 설계했습니다.

핵심 개발

1. 스탯 시스템

스탯 값을 직접 바꾸지 않고 기본값에 수정자 리스트를 적용해 계산했습니다. 바뀌었을 때만 다시 계산하고(dirty 플래그), HP·MP는 최대값 변경 이벤트를 구독해 장비를 바꿔도 현재 값이 어긋나지 않게 했습니다. 장비를 해제하면 출처가 같은 수정자만 제거합니다.

2. FSM 기반 무기, 패링

공격, 패링, 대기를 FSM 상태로 나눠 상태마다 진입, 종료, 전환 조건을 관리하고, 애니메이션 이벤트로 타격 판정과 패링 성공 구간을 맞췄습니다. 무기별 애니메이션은 WeaponMotionData로 분리해 새 무기를 FSM 코드 수정 없이 추가할 수 있습니다.

3. 격자 인벤토리와 마우스 배치

2차원 배열로 칸마다 아이템 참조를 저장해 크기가 다른 아이템의 배치와 충돌을 검사했습니다. 큰 아이템을 잡을 때 포인터가 중심에 고정돼 배치가 어긋나던 문제를, 잡은 칸 기준으로 계산하도록 바꿔 해결했습니다.

문제 해결

🔥 스킬이 늘어날수록 클래스와 중복 코드가 늘어나는 문제
상황

스킬마다 클래스를 하나씩 만들다 보니 데미지, 파티클, 상태이상처럼 같은 효과를 스킬마다 다시 구현하고 있었고, 효과 조합만 다른 스킬도 클래스를 새로 만들어야 했습니다. 포션 같은 아이템에는 스킬 코드를 가져다 쓸 수도 없었습니다.

원인

효과가 스킬 클래스 안에 묶여 있어서 효과만 따로 재사용할 수 없었습니다.

해결
  • 언리얼 GAS가 스킬을 Ability(발동), Effect(효과), Attribute(스탯)로 나눠 데이터로 조합하는 구조를 참고
  • 스킬은 SkillData(데이터)와 SkillBase(쿨타임, 마나 체크)로, 효과는 EffectBase를 상속한 독립 클래스로 분리
  • [SerializeReference]로 인스펙터에서 효과를 골라 리스트로 조합, 즉시 효과와 지속 효과(UniTask)로 구분
  • 프로젝트 규모에 맞춰 GAS의 Tag 시스템과 네트워크 예측은 제외
결과

새 스킬은 기존 효과를 조합해 만들 수 있게 됐고, 같은 효과 리스트를 포션에도 그대로 붙였습니다. 전체 스킬 10종 중 6종은 코드 수정 없이 기존 효과 조합으로 추가했습니다.

알게 된 점

Not Hero 카드에서 썼던 효과 조합 방식을 GAS 구조와 비교하며 스킬 전체로 넓힐 수 있었습니다. 상태이상일 때만 추가 데미지가 들어가는 식의 조건부 효과는 아직 처리하지 못해 다음에 보완하고 싶습니다.

장비를 루팅하면서 적과 총격전을 벌이는 생존 액션 게임입니다. 이전 프로젝트(Not Hero)에서 쓰던 Resources 로드를 Addressable로, object 기반 이벤트를 박싱 없는 제네릭 이벤트로 바꿨고, 팀원이 데이터만 추가하면 새 퀘스트와 아이템이 생기도록 만드는 것을 목표로 했습니다.

핵심 개발

1. 박싱 없는 이벤트 매니저

지난 프로젝트의 이벤트는 매개변수가 object라 박싱 오버헤드가 있고 어떤 타입이 오는지 알 수 없었습니다. IEventData 제네릭 제약과 구조체 이벤트 데이터로 바꿔 박싱을 없애고 정확한 매개변수 타입을 받게 했습니다.

2. Bootstrap 씬 + Additive 씬 컨트롤

DontDestroyOnLoad로 매니저를 유지하면 해제 시점을 계속 신경 써야 했습니다. Bootstrap 씬을 먼저 쌓고 게임 씬을 Additive로 올리는 구조와 빌더 패턴(Fade, 언로드, 데이터 로드, 씬 로드 순)으로 바꿨고, 에디터에서 어떤 씬을 실행해도 Bootstrap 씬과 리소스를 먼저 불러와 팀원이 자기 작업 씬에서 바로 테스트할 수 있게 했습니다.

3. 데이터 기반 퀘스트, 아이템

퀘스트와 아이템을 ScriptableObject 데이터로 분리해, 팀원이 데이터를 추가하고 Addressable에 등록하면 코드 수정 없이 새 퀘스트와 아이템이 생기게 했습니다.

문제 해결

🔥 Resources 로드의 경로 의존성과 메모리 관리 한계
상황

이전 프로젝트에서 빠른 개발을 위해 Resources 폴더를 썼는데, 에셋 위치나 파일명이 바뀔 때마다 코드의 경로를 고쳐야 했고, 폴더 단위로 한꺼번에 로드돼 필요한 것만 올리고 내리기 어려웠습니다.

원인

Resources는 문자열 경로에 직접 묶여 있고, 에셋을 원하는 단위로 묶어서 해제할 방법이 마땅치 않았습니다.

해결
  • Addressable로 바꿔 경로 대신 키로 에셋을 로드, 폴더 구조가 바뀌어도 코드 수정 불필요
  • 로드한 핸들을 딕셔너리로 관리하고, 씬 이름을 라벨로 로드한 뒤 씬 전환 시 모든 핸들을 해제
  • UniTask로 모든 데이터가 로드·캐싱될 때까지 대기해 로드 전 접근 방지
  • ScriptableObject는 원본을 복사해 써서 런타임 수정이 원본 에셋에 저장되는 문제 방지
결과

에셋 경로 변경에 따른 코드 수정이 사라졌고, 씬마다 필요한 에셋만 로드·해제할 수 있게 되었습니다.

알게 된 점

Not Hero에서는 팀원 숙련도와 일정 때문에 일부러 Resources를 골랐는데, 내부 구현만 바꾸면 되도록 캡슐화해 둔 덕분에 바깥 코드는 거의 그대로 두고 교체할 수 있었습니다. 캡슐화가 이후 기술 교체 범위를 줄여 준다는 걸 체감했습니다.

덱을 구성해서 무작위로 생성된 맵을 진행하는 덱빌딩 로그라이크입니다. 카드가 곧 스킬이기 때문에, 카드가 늘어나도 코드 수정 없이 추가하고 조합할 수 있는 데이터 구조와 드로우 연출을 주로 작업했습니다. 여러 명이 동시에 기능을 붙이는 상황이라 매니저 초기화 순서를 직접 잡고 이벤트 매니저로 서로의 코드를 직접 참조하지 않게 했습니다.

핵심 개발

1. 효과를 조합해 만드는 카드 데이터 구조

CardEffect 추상 클래스를 상속한 효과(데미지, 드로우 등)를 [SerializeReference] 리스트로 조합해, 새 카드는 인스펙터에서 효과만 골라 만들 수 있게 했습니다. 카드 설명도 효과 값을 키워드로 자동 생성합니다.

2. 절차적 맵 생성

트리 형태의 노드를 무작위로 연결하되 이웃 노드의 경로와 교차하는지 검사하고, 모든 시작 지점에서 보스까지 경로가 있도록 보장했습니다. 방 종류를 가중치로 정해 매번 다른 맵을 경험할 수 있습니다.

3. 초기화 순서 제어와 이벤트 매니저

Awake / Start로는 매니저 간 초기화 순서를 보장할 수 없어, Managers에서 데이터를 먼저 로드한 뒤 UI, 사운드, 풀링, 전투 순으로 직접 초기화했습니다. 이벤트 매니저로 팀원 간 스크립트 직접 참조를 줄여 협업 효율을 높였습니다.

문제 해결

🔥 연속 드로우 요청 시 카드 연출과 로직이 꼬이는 문제
상황

턴 시작 드로우와 카드 효과로 인한 추가 드로우가 연달아 들어오면, 이전 카드 연출이 밀리거나 손패 정렬과 로직이 꼬였습니다.

원인

드로우 요청이 들어올 때마다 연출을 바로 실행해서, 앞 연출이 끝나기 전에 다음 요청이 끼어들었습니다.

해결
  • 드로우 요청을 큐에 쌓고, 연출이 끝나면 다음 요청을 꺼내 순서대로 처리
  • 손패 수에 따라 카드 위치를 다시 계산해 추가 드로우가 생겨도 정렬 유지
  • 턴 시작·종료는 이벤트로 받아 BattleManager와의 직접 참조 제거
  • 전투 종료 시 모든 카드 트윈을 멈추고 초기화해 의도치 않은 동작 방지
결과

드로우 요청이 연속으로 들어와도 누락 없이 순서대로 연출과 로직이 처리되었습니다.

알게 된 점

연출이 들어간 로직은 요청 시점과 실제 실행 시점이 다를 수 있어서, 큐로 순서를 관리해야 한다는 걸 알게 됐습니다.

카메라로 물체를 인식해 정상품과 불량품을 분류하는 작은 스마트 공장입니다. 3D 프린터로 실제로 움직이는 공장을 만들고, MFC로 만든 프로그램이 컨베이어 벨트, 로봇팔, 운반차를 제어합니다. 정상품은 컨베이어를 계속 지나 로봇팔이 정상 위치로 옮기고, 모양이나 색상이 다른 불량품은 밀어낸 뒤 운반차가 출발합니다.

핵심 개발

1. 장치별 스레드 분리

카메라 출력, YOLO 인식, 컨베이어 벨트, 로봇팔 통신을 각각 별도 스레드(AfxBeginThread)로 돌려 UI가 멈추지 않게 했습니다. 스레드에서 UI를 직접 건드리지 않고 PostMessage로 메인 다이얼로그에 결과를 알립니다.

2. 매니저 구조

WorkManager가 인식 결과를 받아 컨베이어, 로봇팔, 운반차에 작업을 지시하고, DataManager는 정상품과 불량품 개수를 집계, LogManager는 작업 로그를 파일로 저장합니다.

3. 장치 통신과 객체 인식

컨베이어와 로봇팔(아두이노)은 시리얼 통신(115200bps)으로 명령 문자열을 주고받고, 운반차는 Wi-Fi 모듈에 HTTP GET 요청(/start, /wait)으로 제어합니다. OpenCV DNN으로 직접 학습한 YOLO 모델을 불러와 정상품, 모양 불량, 색상 불량을 구분합니다.

🔥 멀티스레드에서 이상한 값이 전송되는 문제
상황

카메라 영상 처리와 시리얼 통신을 동시에 돌리던 중, 장치로 이상한 값이 전송되는 문제가 생겼습니다.

원인

두 스레드가 공유 자원에 동시에 접근하고 있었습니다.

해결
  • 하드웨어부터 의심해 순서대로 테스트하고, 디버깅으로 원인을 추적해 스레드 문제임을 확인
  • 여러 스레드가 함께 쓰는 매니저를 싱글톤으로 만들고 std::mutex로 공유 구간을 보호
결과

전송 값이 섞이지 않고 장치가 정상 동작했고, 3주 안에 목표를 달성해 졸업 작품 최우수상을 받았습니다.

알게 된 점
